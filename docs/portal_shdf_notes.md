## 3. 表单字段与契约 §3 的差异(未实地核验部分如实标注)

**重要:本节字段信息未实地核验。** `report/frontend` 为纯前端渲染页面,静态只读抓取只能得到页面标题
"中国扫黄打非网 - 举报",无法枚举实际控件。以下为公开渠道(第三方指引页)对填写流程的描述,仅供参考:

- 流程:进入网上举报 → 选择举报类别(第三方指引提及存在
  "互联网和手机媒体淫秽色情信息举报"类入口)→ 填写举报人姓名、联系方式 → 按提示输入验证码 →
  阅读并同意举报须知后提交。
- 平台明确"鼓励实名举报,举报信息依法受保护";举报须知含"内容真实性声明"口径。

与 CONTRACTS.md §3 的已知/疑似差异:

1. **入口 URL**:`cfg.portal_shdf_base` 默认值指向主站首页,而真实表单在 `bzpt.shdf.gov.cn`
   子域且为 SPA 路由。部署时应通过 `config.yaml` 把 `portal_shdf_base` 指向实际表单入口
   (建议先指向网上举报栏目页,由人工门环节完成"选择类别→进入表单"的跳转),
   仓库内代码与默认配置保持只含 URL 字符串、绝不发起访问。
2. **选择器**:`SELECTORS` 契约(`#report-url` 等)是本地 mock 与执行器的对接约定;
   真实表单控件 ID/name 未知,预计与契约不一致。上线前需人工核验并在执行器侧增加
   选择器映射层(或改用 computer-use 视觉定位),不得因差异而放松任何红线。
3. **分类文案**:本 planner 固定 `category="淫秽色情类"`(契约 §2);门户实际下拉文案
   第三方指引为"互联网和手机媒体淫秽色情信息举报"字样,**未经实地核验**。若实际文案不同,
   须以门户为准调整 `SHDF_CATEGORY` 或增加文案映射,再走 select 步骤。
4. **字段集合**:契约含 url/type/desc/name/phone/file/captcha/submit;真实表单的附件上传控件、
   字符数限制、必填项均未核验。验证码无论何种形式(图形/短信/滑块),一律只允许 HUMAN_GATE
   人工输入,产品代码绝不自动识别或绕过。
5. **提交流程**:平台为 SPA,提交可能分多步(类别选择页 → 表单页 → 结果页),与契约 §3
   单页固定步骤序列不同,需人工核验后由执行器适配。

## 4. 分类文案备忘

- 契约固定:`淫秽色情类`(`SHDF_CATEGORY`,A14)。
- 平台疑似实际文案:"互联网和手机媒体淫秽色情信息举报"(来源为第三方指引页,未实地核验)。
- 该平台受理范围还包括非法和违禁出版传播、侵权盗版、新闻出版违法违规等类别,
  与本项目无关,填写时注意不要选错。

## 6. 安全红线落实说明

- 本次调研仅"读取公开页面",未注册、未登录、未填写、未提交任何内容;
  开发/测试期间未以自动化方式访问真实表单页(静态只读阅读服务除外,未执行其 JS)。
- `netsentinel/submit/portal_shdf.py` 只生成声明式计划,不发起网络请求;
  入口 URL 一律取 `cfg.portal_shdf_base` 或调用方显式传入值,产品代码不硬编码真实门户地址。
- 计划中验证码环节仅为 HUMAN_GATE(人工输入),模块内置红线自检:
  缺人工门或出现自动填验证码步骤时直接拒绝生成计划(抛中文 RuntimeError)。
